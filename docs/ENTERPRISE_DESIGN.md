# Yuval — enterprise design contract

This file is the single source of truth for the enterprise refactor of PILLAR.
Implementation agents MUST follow it. If something here is wrong, stop and report; do not diverge silently.

Island has no text inputs in V1, so no activation toggle is needed. Since 1.0.4 there is one more `AllowSetForegroundWindow`, in `center::open`: only for the process id of the Yuval Center (the connected pipe client, or the child it just started), only right after a user click (an island button, the tray item) or at the first run, never `ASFW_ANY`. The island itself still never takes focus; the Center is an ordinary window that comes forward on its own. |

Fired-set persisted per user in `state\reminders.json`, key `"<eventHash>|<startUtcIso>|<reminderType>"`, pruned after 7 days. A missed window (PC asleep) fires late only if event hasn't started and ≥ 1 min remains; otherwise marked skipped. |

| Yuval Center (1.0.4) | A real WinUI 3 app, chosen by the user on 2026-10-06 over more panels inside the island: `center/` in the repo, C# on .NET 10, Windows App SDK 1.8 unpackaged (`WindowsPackageType=None`), self-contained and trimmed (`PublishTrimmed`, `TrimMode=partial`), x64. Versioned together with the island (`center/Directory.Build.props` is checked by `scripts/check-versions.cjs`). |
| Center IPC | The Center talks to the island only through a local named pipe served by the island's Rust backend (`center_ipc.rs`). Name `\\.\pipe\CompanyIsland.Center.<sessionId>.<sidhash>`, `sidhash` = first 16 lowercase hex chars of SHA-256 over the user's SID string. Security: protected DACL `D:P(A;;GA;;;<user SID>)` (only this user, not even Administrators), `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE` (a squatted name means `APP-031` and no server; the island keeps working), at most 4 instances, byte mode; every accepted connection must report this process's Windows session id (`GetNamedPipeClientSessionId`) or it is dropped; the client side opens with `PipeOptions.CurrentUserOnly`. Rust stays the only writer of both files; the Center's requests go through the same functions the island's own commands use (side effects included). Request and response bodies are never logged (command names and connect/disconnect at debug level only). |
| Notes (1.0.4) | The first user-written content the product keeps on disk: `%LOCALAPPDATA%\Yuval\state\notes.json`, per user, `{"schemaVersion":1,"notes":[{id,text,createdAt,updatedAt,pinned}]}` (a bare array is also accepted on load). Rust (`notes.rs`) is authoritative and sanitises every save and every load: id 1..64 chars of `[A-Za-z0-9_-]` (else dropped); text kept exactly as typed, but a note whose trimmed text is empty is dropped and text over 10,000 characters (Unicode scalar values) is cut at a character boundary; timestamps <= 0 become now and `updatedAt` is never before `createdAt`; a duplicate id keeps the larger `updatedAt`; at most 500 notes (the 500 with the newest `updatedAt`); canonical order everywhere = pinned first, `updatedAt` descending, id ascending. File limits: a result over 16 MiB is refused (`APP-002`) and a file over 16 MiB or unparsable is quarantined as `notes.json.corrupt` (`APP-003`, empty list). Atomic write (temp file + rename), one static lock serialises load and save. Note text is user content: never logged (counts only), never sent anywhere, kept on uninstall like the rest of the per-user data. |
| First run (1.0.4) | Setting `onboardingDone` (default false; a `settings.json` from before 1.0.4 has no such key, so every upgrader sees the Welcome page once too). In `lib.rs` setup, while it is false, a short-lived thread (`companyisland-onboarding`) waits 1.5 s and calls `center::open("welcome")`; only when that succeeded is `onboardingDone: true` written, so a Center that is missing or fails (`APP-030`) is retried at the next start. After that the Center opens only on a click (tray item, island buttons, a note). |
| Island display (1.0.4) | Setting `islandDisplay`: `full` (default: date, a small clock, weekday), `clock` (time only) or `date` (date and weekday, the pre-1.0.4 look). Any other value is sanitised to `full` in Rust (`settings.rs`) and in `normalizeSettings`. It is changed in the island's Settings tab or the Center's Settings page and applies live to both through `settings-changed`. Looks and sizes are in section 2. |
| Tour (1.0.4) | A React page (`tour.html`, `src/tour/`) built by Vite into the same `dist/` as the island, copied by `scripts/build-center.cjs` to `center\web\` and shown in the Center's WebView2 through the virtual host `https://tour.companyisland.invalid/tour.html` mapped to that folder. 12 steps built from the island's real components and mock data. It has no IPC and no network: its CSP is `default-src 'self'; ...; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`, the stage is `inert` and swallows clicks, and the host cancels any navigation to another origin, new windows, downloads and permission requests. |

## 1. Rust ⇄ TypeScript contract

All commands are registered in `lib.rs` `invoke_handler`; Rust modules live in `src-tauri/src/`.
Command errors are `Result<T, String>` where the string is `"CODE: short message"` with a stable code (see §3).

### Commands
- `get_system_info() -> SystemInfo`
- `get_format_locale() -> string | null` (BCP-47 regional format tag), `get_fullscreen_state() -> bool` (the event only reports changes; the page asks once on mount)
- `get_diagnostics() -> Diagnostics` (privacy-safe: no subjects, no emails)
- `copy_text_to_clipboard(text: String) -> ()` (Win32 clipboard; no webview focus needed)
- `open_log_dir() -> ()`
- `get_settings() -> Settings`, `update_settings(patch: SettingsPatch) -> Settings` (single Rust `SettingsStore`, validated, schema-versioned, atomic write, emits `settings-changed`)
- `calendar_get_snapshot() -> CalendarSnapshot`, `calendar_refresh() -> ()`
- `outlook_respond_invite(id: string, response: "accept" | "tentative" | "decline") -> ()` — only from a click. The request's EntryID is looked up in Rust memory by the hashed id from the latest read (never sent to the page); `GetItemFromID` → `GetAssociatedAppointment(true)` → `Respond(olMeetingAccepted 3 / Tentative 2 / Declined 4, fNoUI=true)` → `Send()` on the reply when `ResponseRequested` (unknown counts as yes). Own STA thread, 60 s limit (Outlook may show its own security prompt), then a calendar refresh. Errors `OUTLOOK-101/103/104/105/108/109/110`.
- `open_meeting_url(url: string) -> ()` — only from a click on Join, and only for a link the backend itself reported (https from a meeting property, or a known meeting host from a Location; `APP-020` otherwise). Teams web links go to the Teams app (`msteams:`) when it is installed, everything else to its default handler via `ShellExecuteW`. The link is never logged.
- `calendar_get_range(fromUtc: string, toUtc: string) -> CalendarEventDto[]` — a day the user browses to in the Calendar tab (at most 7 days per call). Served by the same STA worker and watchdog as the sync (queued behind a running read), only while connected; nothing is cached in Rust and the machine (and so reminders) is untouched. The page keeps each day for 2 min.
- `outlook_open_calendar(startUtc: string | null) -> ()` — only from a click on a meeting invitation. Attach-only (a closed Outlook is not started; `OUTLOOK-101/103/104`), on a fresh STA thread, 10 s limit (`OUTLOOK-109`): `ActiveExplorer.CurrentFolder = default calendar` (or `GetExplorer` + `Display` when Outlook has no main window), restore if minimized, `AllowSetForegroundWindow(outlook pid)` + `Activate`, then `CalendarView.GoToDate(local day of startUtc)`.
- `reminder_state_load() -> Record<string, number>` (key → firedAtUnixMs), `reminder_state_save(map)`.
- `notes_load() -> Note[]` (missing, unreadable or corrupt file = `[]`), `notes_save(notes: Note[]) -> Note[]` — replaces all notes with the sanitised list (section 0, Notes), returns it in canonical order, then emits `notes-changed`. Errors `APP-002` (cannot write, also "too large"); a corrupt file is `APP-003` at load. Both run on the blocking pool.
- `open_center(page: string) -> ()` — only from a user click or the first run (never from a timer). `page` is `welcome`, `tour`, `settings`, `notes`, `notes-new` or `note:<id>` (`APP-032` otherwise). When a Center is connected on the pipe it gets a `navigate` event (after `AllowSetForegroundWindow` for that client's pid); otherwise `<dir of Yuval.exe>\center\Yuval.Center.exe --page <page>` is started by absolute path, no shell, not waited on, then `AllowSetForegroundWindow(child pid)`. A missing exe or a failed start is `APP-030`. Debug builds only: the env var `COMPANYISLAND_CENTER_EXE` (absolute path) replaces the exe location.
- `notifications_get_status() -> NotificationStatus`, `notifications_request_access() -> NotificationStatus` (only on explicit user click), plus existing notification list/activate commands, trimmed.
- Window: `set_island_geometry(width, height, radius, stageWidth, stageHeight)` (flat logical px; the native window is a fixed stage as large as the largest island, never resized or moved while the island animates; a rounded SetWindowRgn cut to the island's resting shape makes the rest of the stage click-through; no global mouse hook), `get_monitors() -> [{id,name,primary,isPrimary,width,height,scale}]`; setting key is `monitorId` (null = primary).

### Events (Rust → JS)
- `calendar-snapshot` (payload `CalendarSnapshot`) — emitted on every state change and after each successful sync.
- `notification-received`, `notification-status`
- `settings-changed`, `fullscreen-changed`, `display-changed`, `island-toggle` (from tray / second instance; also from the Center's `showIsland`, with a tab)
- `notes-changed` (payload `Note[]`) — after every successful notes save, whoever made it (the island's tab or the Center); the island's notes store replaces its confirmed list with it.
- `foreground-changed` (no payload) — another process's window became active; forwarded from the fullscreen module's existing out-of-context `EVENT_SYSTEM_FOREGROUND` WinEvent hook. Closes the island on a click outside it without any mouse hook.

### Types (camelCase over IPC; Rust uses `#[serde(rename_all = "camelCase")]`)

### Yuval Center pipe (protocol 1)

Transport and security are in section 0 (Center IPC). Each line is one JSON object.
Request `{"id": 1..2^53, "cmd": "<name>", "args": {...}}` (`args` optional); response `{"id", "ok": true, "result": ...}` or `{"id", "ok": false, "error": "CODE: short message"}`; event `{"event": "<name>", "payload": ...}` (no id). A line that is not JSON or has no usable id is answered with `"id": null` and the connection stays open; unknown fields are ignored. Requests of one connection are handled one after another; blocking work runs on the blocking pool.

| cmd | args | result |
|---|---|---|
| `hello` | `{"client":"center","protocol":1}` | `{"protocol":1,"appVersion":"<version>"}`. Must be the first request (`APP-031: hello required`); another protocol is `APP-031: unsupported protocol`. Marks the connection as a Center client. |
| `getSettings` | none | `Settings` |
| `updateSettings` | `{"patch": SettingsPatch}` | `Settings`; the same path as `update_settings`, so every side effect (autostart, log level, monitor, fullscreen, notifications) happens |
| `notesLoad` / `notesSave` | none / `{"notes": Note[]}` | `Note[]` (sanitised, canonical order) |
| `getMonitors` | none | `MonitorInfo[]` |
| `getNotificationStatus` / `requestNotificationAccess` | none | `NotificationStatus`; the request only from an explicit click in the Center |
| `openLogDir` | none | `null` |
| `showIsland` | `{"tab": "calendar"\|"notifications"\|"notes"\|"about"\|"settings"}` (the Center always sends one) | `null`; shows the island and expands it on that tab |
| `log` | `{"level":"info"\|"warn"\|"error","message":string}` | `null`; the message is clipped to 300 characters and written with the scope `center`. The Center sends codes and names only, never user content. |

An unknown command or bad arguments are `APP-031: unknown command` / `APP-031: invalid arguments`. Events: `settings-changed` (`Settings`, after every settings change, whoever made it) and `notes-changed` (`Note[]`) to every client that completed `hello`; `navigate` (`{"page": CenterPage}`) to Center clients only, always preceded by the foreground grant for that client's pid. A client whose queue falls 256 lines behind is disconnected (`APP-031`). The Center reconnects by itself (about every 3 s) and shows "the island is not running" with its inputs disabled while it cannot connect.

## 2. Frontend architecture

```

src/tour/, tour.html          the tour page (section 0, Tour): TourApp, TourStage, steps, mock data, host messages

```
Interaction: no global mouse hook. The native window's region is exactly the island's resting shape (`set_island_geometry`, inside a fixed stage window), so DOM pointer events are the island's own: hover (120 ms intent) expands, leave collapses (400 ms once the pointer has been on it, clicked or not; 4 s for an island opened from the tray / second launch that the pointer has not reached), a click outside it (desktop, taskbar, another app) collapses it at once via `foreground-changed` (the window is non-activating, so that click activates another window), a meeting alert (8 s) or toast (4.5 s) pauses while hovered.
Rules: no Tauri `invoke` inside React components (only through `src/lib/*` / hooks). No Outlook logic in React. UI talks to `CalendarProvider` only.

## 4. Local IPv4 selection strategy (documented, deterministic)
1. `GetAdaptersAddresses` (IPv4, skip DNS suffix/multicast), keep adapters with `IfOperStatus == Up`, not loopback/tunnel (`IF_TYPE_SOFTWARE_LOOPBACK`, `IF_TYPE_TUNNEL`), unicast address not `127/8`, not `169.254/16`.
2. Drop adapters whose description/friendly name matches virtual patterns (Hyper-V vEthernet, VirtualBox, VMware, Tailscale, WSL, Docker, TAP/TUN, Npcap/loopback, Bluetooth PAN) unless nothing else remains.
3. Prefer the adapter that owns the lowest-metric default IPv4 route with a non-zero gateway (`GetBestRoute2`/`GetIpForwardTable2`); VPN adapters rank below physical ones.
4. Ties: Ethernet (type 6) > Wi-Fi (71) > other; then lowest interface metric; then lowest IfIndex.
5. If nothing qualifies, fall back to APIPA only if no other IPv4 exists, else `null` (`NET-301`). Result cached; recomputed on `NotifyIpInterfaceChange` or every 60 s while About is visible — never polled while collapsed.

## 5. Privacy rules (apply everywhere)
No meeting subjects/locations/organizers (of events or meeting invitations) in logs, diagnostics, crash reports or persisted caches; invites are held in memory only, and the "already shown" set is in memory only too. Logs may contain: event hash (first 8 hex), counts, timings, error codes. The reminder store holds only hash|start|type|firedAt. There is no persistent event cache on disk in V1 (events are re-read from Outlook's own local cache on attach).

Notes (1.0.4) are the one kind of user content that is kept on disk, and only because the user typed it there: `%LOCALAPPDATA%\Yuval\state\notes.json`, plain JSON, readable by that user only through the profile's own permissions, at most 500 notes of 10,000 characters and 16 MiB in all, never leaves the machine. It is kept when the product is uninstalled (like every per-user file) and removed by the per-user wipe in [DEPLOYMENT.md](DEPLOYMENT.md) section 7. A corrupt file is renamed `notes.json.corrupt` (a copy of what the user typed stays on disk until they delete it) and the list starts empty. Note text is never in a log, a diagnostic, the pipe's `log` command or a Tauri event other than `notes-changed` (which stays inside the app: the island's page and the Center's own pipe); logs hold counts ("saved 12 notes"), codes and, for `open_center`, only the page kind (`note`, never the id). The pipe carries only what the user asked for: settings, notes, monitor list, notification status, `showIsland`; request and response bodies are not logged, and the Center's `log` messages are codes and names. The tour has no IPC (no pipe, no Tauri bridge) and no network (`connect-src 'none'`, virtual host that serves only `center\web\`); it shows invented sample meetings and notes, never real ones.

## 7. Windows 10 21H2 (build 19044) compatibility and runtime hardening

Audited from the built exe's import table and the Rust sources. Nothing needs anything newer than Windows 10 1607 (build 14393); the one 1607 dependency is `UserNotificationListener`, which is best effort by design (§0).
